## Prompt 15 — Monogram rendering artifact

```
OBJECTIVE: The identity monogram (NilMonogram.svelte, welcome screen
and cold-open) has "transparent lines going through it" per live
feedback — visible seams/gaps in what should be a solid pixel-grid
mark.

CONTEXT: The monogram is generated by monogramGrid.ts's monogramCells()
and rendered as inset SVG rects in NilMonogram.svelte (ported from the
wireframe in PR #40). Each cell is likely an individual <rect> with
its own fill; adjacent rects can show a seam line between them from
anti-aliasing or sub-pixel gaps if they don't share exact edges, or if
there's a stroke/gap intentionally separating cells that reads as
"broken" rather than "grid-styled" at the rendered size. Check both
the SVG rendering (NilMonogram.svelte) and the canvas rasterization
(ColdOpen.svelte uses the same grid data) — the bug may only affect
one of the two renderers.

SCOPE: NilMonogram.svelte and/or ColdOpen.svelte's use of
monogramGrid.ts. Do not change monogramGrid.ts's cell data itself
(monogramGrid.test.ts pins the mirror-symmetry invariant — a rendering
fix should not need to touch cell generation).

VERIFICATION: npm run check, npm run build. Screenshot the welcome
screen's monogram at 2x zoom (or crop tightly) before/after to confirm
the seams are gone.

STOP CONDITION: The monogram renders as a solid mark with no visible
seams between cells, verified via screenshot comparison.
```

## Prompt 17 — Mode-segment pill clips past its track on switch

```
OBJECTIVE: The Build/Pentest segmented pill (JELLY primitive, #11)
visibly clips past the button edge when switching per live feedback —
it should morph and never travel outside the track's bounds.

CONTEXT: JELLY is driven by element.animate() with keyframes anchored
via --jelly-origin at the component level (StreamComposer.svelte,
per motion.css's own primitive doc). The clip is likely either (a) the
overshoot keyframe genuinely translating the pill past the track's
own edge because the track container doesn't have overflow:hidden, or
(b) the width/position math not accounting for the pill's own width
when computing the landing transform. Read the JELLY primitive comment
in motion.css in full before touching the keyframes — it documents
exactly why this is JS-driven (transform-origin can't reverse mid-
transition in CSS alone) and what --dur-jelly/--ease-pop are for;
don't invent a different curve, fix the bounds.

SCOPE: The mode-segment pill only (StreamComposer.svelte + jelly.ts).

VERIFICATION: npm run check, npm run build. Switch Build→Pentest→Build
rapidly a few times and confirm the pill never renders outside the
track.

STOP CONDITION: The pill stays within its track through the full
animation on every switch direction, verified visually across several
rapid toggles (not just one slow one).
```

## Prompt 18 — Model chip text centering + segment border rendering at 1080p

```
OBJECTIVE: Two related small visual bugs in the composer toolbar:
(a) the "Harness default" model-chip button's text isn't vertically
centered in its pill, and (b) the Build/Pentest segment's borders are
reported as "very tiny and interact oddly" specifically on a 1080p
display — likely a sub-pixel border-width issue (a 1px border can
round to 0 or double depending on devicePixelRatio and the exact
computed height of the pill).

CONTEXT: Both live in StreamComposer.svelte's toolbar
(.model / .segment / .seg classes). For (a), check the button's
line-height and padding — a flex row without align-items: center, or
an odd font-size/line-height combination, is the usual cause. For (b),
check whether the border uses a plain `border: 1px solid` on an
element with a non-integer computed height (odd height + 1px border
can produce a blurry/inconsistent line at 1x DPI, which is exactly a
1920x1080 non-Retina display) — box-shadow-as-border (0 0 0 1px) at an
integer pixel boundary is the usual fix.

SCOPE: StreamComposer.svelte's toolbar only.

VERIFICATION: npm run check, npm run build. Check computed height of
the segment/chip elements is an integer via getBoundingClientRect() —
non-integer heights are the likely root cause of (b) and worth
confirming before guessing at a border-rendering fix.

STOP CONDITION: Model-chip text is vertically centered; segment
borders render as a crisp, consistent 1px line. Verified via
getBoundingClientRect() height check, not just a screenshot.
```

## Prompt 20 — xterm's hidden helper textarea is visible and intrusive

```
OBJECTIVE: xterm.js's internal helper textarea (used for keyboard
input capture — it's supposed to be invisible/off-screen) is showing
up as a visible, clickable, oddly-contrasting element per live
feedback: "not only hard to click on but has icons and very visible
contrasting terminal."

CONTEXT: This is almost certainly a CSS specificity or z-index
collision — xterm.js ships its own stylesheet that positions
.xterm-helper-textarea off-screen (typically position:absolute with
huge negative offsets or opacity:0), and something in NIL's own CSS is
likely overriding or not cascading correctly against it, OR the
textarea's coordinates are being computed relative to the wrong
container after NIL's terminal wrapper styling changed its positioning
context. Check TerminalTab.svelte and wherever xterm's CSS is
imported — confirm xterm's own stylesheet is actually loading (a
missing import would explain the textarea rendering with browser
default styles: visible, with a normal focus ring, etc.).

SCOPE: TerminalTab.svelte and its xterm integration/imports only.

VERIFICATION: npm run check, npm run build. Open a terminal dock and
confirm the helper textarea is not visible or interactable as a
distinct element (it should be functionally present for keyboard
capture but visually imperceptible, exactly as xterm.js intends).

STOP CONDITION: The helper textarea is invisible and doesn't interfere
with clicking the actual terminal surface, verified visually and by
confirming keyboard input to the terminal still works after the fix
(don't just hide it and break input capture).
```

## Explicitly deferred, not in scope for any prompt above

These four are real feedback but need a design decision or a bigger
rework than a single scoped prompt should attempt blind — they're
listed here so they aren't lost, not because they don't matter:

- **The composer's focus border** ("border beam is not a gradient that
  is dynamic and shapes INTO the text area, just awkwardly scrolls
  around it") — this is the chromatic prism ring documented as a
  sanctioned Law 1 exception in StreamComposer.svelte's CSS comments
  ("Charter amendment 2026-09-07"). Changing its actual animation
  shape (not just tuning existing values) is a motion-design call, not
  a bug fix — bring it to the user with 2-3 concrete alternatives
  before implementing.
- **The stream/log area feels like a raw terminal, not "clean like
  Claude's desktop app"** — this is the single biggest piece of
  feedback in the batch (items 14 and 25) and touches AgentStream.svelte
  and how tool output/messages render generally. It's a real design
  direction question (how much of the "hacker terminal" aesthetic is
  intentional NIL identity vs. accidentally under-designed) that
  should go back to the user before any prompt attempts it — get their
  answer, then write a properly scoped prompt.
- **Model picker categorization by complexity/reasoning, "More models"
  as an afterthought, effort switcher polish** (items 16-19) — this is
  a product/IA decision (what models are actually offered, how they're
  grouped) tangled with visual polish. Also needs the user's input on
  what the real model list should be before a prompt can scope the UI
  around it.
- **"Flat background, no depth coloring, just feels sad"** — the
  broadest, vaguest item in the batch. Worth a real design pass once
  the more concrete items above are cleared, not a blind prompt.
